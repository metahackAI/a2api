# a2api MVP와 평가 계획

작성일: 2026-10-28 · 상태: 제안

## 1. 첫 구현의 범위

첫 목표는 하나의 실제 도메인에서 **API 검색·조립·실행·설명까지 이어지는 작은 경로**를 완성하고 효과를 측정하는 것이다. 모든 언어용 분석기와 분산 workflow 엔진을 동시에 만드는 것은 후속 범위로 둔다.

초기 샘플 규모는 HTTP operation 20~40개, 업무 capability 5~10개, 과제 50개 내외를 제안한다. 이 숫자는 확보된 데이터가 아니라 실험 규모의 출발점이다. 실제 레포와 도메인을 확인한 뒤 조정한다.

우선 주문·배송 조회처럼 여러 호출을 조립하고 모호한 식별자를 다루는 조회 업무를 선택한다. 이후 격리 환경에서만 주문 취소 같은 변경 업무를 추가한다. 실제 업무 도메인이 다르면 구조를 유지하고 예제를 교체한다.

## 2. 초기 기술 선택 제안

| 영역 | 시작안 | 선택 이유·후속 조건 |
|---|---|---|
| 계약 표현 | JSON과 JSON Schema, 필요하면 YAML 입력 | 언어 중립, 원본과 생성물 diff 확인 |
| compiler·runtime·CLI | TypeScript 우선 검토 | JSON 계약·도구 bridge를 한 구현으로 실험하기 쉬움. 팀 환경 확인 후 확정 |
| 연결 | 기존 HTTP 우선 | backend 구현 언어와 독립적으로 검증 가능 |
| registry | 파일 snapshot 또는 SQLite | 초기 운영 요소를 줄이고 쿼리로 한계를 측정 |
| 검색 | 키워드·태그 baseline, 이후 의미 검색 추가 | 검색 품질과 추가 비용을 각각 측정 |
| 실행 | 프로세스 내 라이브러리, 선택적 HTTP/MCP gateway | 라이브러리 목표와 다중 언어 접근을 함께 지원 |
| 소스 분석 | 명세·route 중심, AST는 부족한 구간부터 | 전체 소스 자동 이해를 선행 조건으로 만들지 않음 |

MCP SDK나 validator의 구체 버전은 구현 시 지원 범위를 확인해 고정한다. 최신 표준이 존재하는 것과 라이브러리가 그 기능을 구현하는 것은 다르다.

첫 importer는 OpenAPI 3.0/3.1에서 지원하는 기능을 명시하고, 3.2 및 그 밖의 기능은 실제 fixture와 parser 지원을 확인해 확장한다. 지원하지 않는 버전·키워드는 진단하며 조용히 downgrade하지 않는다.

## 3. 단계별 산출물과 완료 조건

| 단계 | 산출물 | 완료 조건 |
|---|---|---|
| 0. 실제 대상 조사 | 레포 연결, API·서비스·소유자 inventory, 대표 업무 | 조사 범위·미지원 경계·실행 가능한 테스트 환경을 확인 |
| 1. 계약 core | manifest schema, IR, validator, 수동 capability | 미검토·미지원 계약을 거부하고 fixture의 입력·출력 검증 |
| 2. 한 경로 연결 | HTTP adapter, 동기 invoke, 결과 envelope | 원시 API와 capability 결과를 같은 fixture에서 비교 |
| 3. 점진 탐색 | discover/describe, 태그·검색·권한 filter | 관련 기능 발견률과 노출 토큰 수 측정 |
| 4. 조립·그래프 | 검토한 의미 타입·관계, bounded DAG, 예산 | 잘못된 ID 매핑·순환·과도한 fan-out 검출 |
| 5. 표준 bridge | 고정 버전 MCP bridge, 선택적 직접 도구 노출 | 대상 호스트의 실제 discovery·call·결과 schema 검증 |
| 6. 레거시 자동화 | OpenAPI importer, overlay 분리, 증분 재생성 | 원본 변경 영향 추적 및 사람의 검토 내용 보존 |
| 7. 변경 업무 | prepare/commit, 결과 대조, 제한한 보상 | 중복 요청·응답 유실·경쟁 상태를 격리 환경에서 검증 |
| 8. 확대 | 추가 importer·SDK·이벤트 binding | 언어·규모를 늘렸을 때 적합성과 운영 비용 재평가 |

각 단계는 작은 실제 경로를 끝까지 연결한다. 명세 파일만 많이 생성한 상태를 완료로 삼지 않는다. 일정은 실제 레포 규모와 팀 역량을 파악한 뒤 산정한다.

## 4. 비교 실험

그래프와 설명 개선의 효과가 섞이지 않게 실험군을 나눈다.

| 군 | 조건 | 확인할 질문 |
|---|---|---|
| A | 기존 operation을 평면 도구로 노출 | 직접 사용의 기준 성능과 문맥 한계는 무엇인가 |
| B | 검토한 설명·타입 + 검색, 평면 카탈로그 | 설명 보강과 후보 축소가 얼마나 기여하는가 |
| C | B와 같은 계약·검색 + 의미 관계 그래프 | 그래프 자체가 순서·입력 연결을 개선하는가 |
| D | C + 검토한 composition을 런타임 실행 | LLM의 반복 계획을 줄였을 때 성공·비용 변화는 무엇인가 |
| E | 같은 업무의 native backend 구현 | backend 보장과 업무 API 재설계가 더 필요한 구간은 어디인가 |

B와 C는 설명·스키마·모델·예제를 동일하게 유지한다. A~D의 backend 데이터와 권한 집행도 동일하게 둔다. baseline에서 보호 장치를 제거해 실험하지 않는다.

E에서 원자 operation 수나 backend 기능이 달라지면 별도 요인으로 보고한다. 이를 그래프 개선으로 귀속하지 않는다. 수동 작성과 자동 추출 계약도 별도 비교해 전환 품질을 평가한다.

모델 버전, prompt, 문맥 한도, temperature, 시간 제한, 재시도 정책, 검색 인덱스 snapshot을 고정한다. 동일 과제를 여러 번 실행하고 과제 유형별 결과와 변동을 기록한다. 정답을 만드는 데 쓴 예제와 평가 과제는 분리한다.

도구 수 실험은 실제 API에 유사 이름·유사 타입의 방해 후보를 추가해 단계적으로 늘린다. 합성 후보의 결과를 실제 대규모 서비스 운영 성능과 구별한다. 전체 스키마가 문맥에 들어가지 않는 A는 입력 불가 또는 초과로 기록하고 몰래 잘라내지 않는다.

## 5. 평가 과제와 지표

과제에는 단일 조회, 2~5단계 조립, 대안 경로, 모호한 고객, 다른 테넌트의 ID, 빈 결과, 페이지 일부, 부분 실패, timeout, 계약 변경을 포함한다. 변경 업무에는 중복 요청, commit 직전 상태 변경, 성공 후 응답 유실을 추가한다.

| 평가 대상 | 지표 |
|---|---|
| 검색 | 정답/대안 capability recall@k, 권한별 노출 오류 |
| 선택·연결 | 유효 operation 선택률, 입력·의미 타입 오류, 선행 조건 누락 |
| 업무 결과 | end-to-end 성공률, 올바른 추가 질문/실행 거부율 |
| 설명 품질 | 구조화 사실과 답변 일치, 출처·기준 시각·부분 결과 표시 |
| 부작용 | 중복 변경·범위 밖 변경·권한 위반의 관측 건수 |
| 비용 | 도구 설명 토큰, LLM 호출 수, backend 시도 수, 지연 p50/p95 |
| 전환 비용 | 추출 항목 검토 시간, 관계 오탐, 원본 변경 후 재검토량 |
| 운영성 | 실패 원인 추적률, 계약 drift 감지, rollback/disable 소요 |

성공 판정은 HTTP 200 또는 JSON schema 통과에 그치지 않는다. fixture의 실제 상태·읽은 대상·반환 데이터·허용한 효과와 비교한다. 가능한 한 결정적 검사를 사용하고, 주관적인 답변 표현 평가는 별도로 수행한다.

안전 관련 과제에서는 위반 0건을 출시 조건으로 제안하되, 유한한 테스트에서 0건이라는 뜻이다. 현실 전체의 무오류 보장으로 표현하지 않는다. 성공률·지연 개선의 수치 목표는 baseline 측정 후 정한다.

## 6. 반드시 확인할 구현 경계

- wrapper가 backend의 멱등성·원자성까지 보장한다고 표시하지 않았는가.
- 조회 capability가 다른 사용자의 데이터나 과도한 개인정보를 반환하지 않는가.
- 잘못된 graph edge가 실제 호출로 이어지기 전에 차단되는가.
- 외부 응답의 명령형 문구가 policy·대상·credential 선택을 바꾸지 못하는가.
- 결과를 확정할 수 없는 요청이 `unknown`으로 남고 대조 가능한가.
- 계약·카탈로그 교체 시 검색과 실행의 버전이 일치하는가.
- 출력 마스킹과 사용자 표시 설정이 실제 전송 범위와 일치하는가.

이는 이 문서에서 실행한 보안 검사 결과가 아니라 향후 런타임 적합성 요건이다.

## 7. 설계 결정과 남은 선택

현재 권고하는 결정은 하나의 IR, 명세 우선 수집, 검토한 관계만 실행, 기존 전송 표준 재사용, 업무 성공률 중심 평가다.

실제 개발 착수 전에 확인할 선택은 첫 업무 도메인, 허용하는 원본 소스 범위, 배포 형태, 팀의 초기 구현 언어, 필요한 인증 위임 방식이다. 현재 설계는 이 선택에 종속되지 않도록 구성했다.

완전 자동 변환, 모든 언어의 완전한 정적 분석, 임의 workflow 생성, 모든 시스템의 분산 트랜잭션은 초기 제공 범위에 넣지 않는다. 각 기능은 측정한 필요와 보장 가능한 계약을 기준으로 확장한다.
