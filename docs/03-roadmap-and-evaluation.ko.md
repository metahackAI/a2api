# a2api 개발 계획: 전환 모듈을 먼저 끝내기

갱신일: 2026-10-29 · 기준: [제품 방향과 전환·호출 설계](00-product-direction.ko.md)

현재 최신 요청인 [실제 GitHub 검증](26-real-github-evaluation-plan.ko.md)은 완료했다. [결과](27-real-github-evaluation-results.ko.md)는 소규모 성공과 대규모 탐색 실패를 구분하며, [후속 개선 계획](28-cost-improvement-plan.ko.md)은 아직 구현하지 않았다. 이번 요청은 검증·개선 계획까지이며 후속 제품 변경을 자동 시작하지 않는다.

이전 [전체 호출 비용 계획](23-total-call-cost-plan.ko.md)의 호스트 바인딩과 제한된 합성 카탈로그 비교는 완료 이력이다. 아래 완료된 작업도 이력으로 보존한다. 운영 플랫폼이나 추가 importer 개발을 완료 조건에 넣지 않는다.

과거의 넓은 로드맵을 이 계획으로 대체했다. 현재 **P0-1/2/3 구현 완료**이며 [OpenAPI 호출](11-in-memory-conversion.ko.md), [Python 함수 등록](12-python-functions.ko.md), [경량 MCP 연결](13-lightweight-mcp.ko.md) 안내가 있다.

## 1. 목표와 기본 사용 경험

지원하는 API를 가져와 작은 설정으로 전환하고 바로 호출한다.

```text
OpenAPI/등록한 코드 → convert → invoke
                           └→ 필요하면 같은 객체를 MCP에 연결
```

사용자가 필수로 작성할 것은 노출할 API 선택, 실제 연결 정보와 필요한 입출력 정의다. 검토 파일·build 디렉터리·변경 감지·재승인·재배포를 모두 요구하지 않는다. 내부 모듈 분리는 사용자 작업 단계를 늘리는 근거가 아니다.

## 2. 첫 모듈 완료까지의 개발 단위

병렬 프로젝트를 새로 만들지 않고 다음 세 결과를 순서대로 완성한다. 모두 같은 공개 호출 계약과 실행 모듈을 사용한다.

| 순서 | 실제 사용 결과 | 완료 기준 |
|---|---|---|
| **P0-1 완료** | **OpenAPI의 선택한 GET/HEAD를 메모리에서 변환해 호출** | 작은 descriptor와 서버 binding을 구분한다. `convert(source, operations=..., deployment=...)`가 반환한 객체로 주문·배송 원자 API를 호출한다. 별도 review/build/snapshot이 필수가 아니다. 기존 인증·입력·응답 검증은 유지한다. |
| **P0-2 완료** | **명시적으로 등록한 Python 함수·신규 API도 같은 방식으로 호출** | 지원하는 signature/TypedDict 등에서 schema를 생성하고 callable을 연결한다. 같은 프로토콜로 기존 함수 wrapper와 신규 함수가 모두 실행된다. 지원 불가 타입은 명시적 schema를 요구한다. |
| **P0-3 완료** | **전환한 객체를 MCP에서 작은 설명으로 호출하고 사용자 가이드 완성** | 실제 stdio에서 discover/describe/invoke를 실행한다. MCP tools/list가 전체 business schema를 나열하지 않는다. 기본 describe는 agent descriptor만 반환한다. 일반 앱 연결 예제와 현재 실행 가능한 시작 문서를 제공한다. |

P0-3 이후 이번 요청은 **기존 GitHub OpenAPI로 공개 저장소 조회·이슈 목록 조회를 연결하는 실사용 예제**로 제한한다. 기존 `convert`/`capability`로 필요한 필드만 반환하고 실제 API·MCP stdio를 검증한다. [사용 문서](14-github-readonly-example.ko.md)에 실행법과 한 페이지 범위를 기록한다. 핵심 모듈 확장이나 새 관리 단계는 추가하지 않는다. 후속 범위는 사용자의 다음 지시를 따른다.

해당 예제 완료 후 사용자가 지시한 다음 개발은 **실제 LLM의 GitHub MCP 사용 검증**이다. [상세 개발 계획](15-agent-usage-plan.ko.md)에 파일·질문·수정 허용 범위·완료 기준을 고정했다. 문서의 1 → 2 → 3 → 4 순서대로 끝내며 계획 밖의 확장 후보를 구현하지 않는다.

2026-10-30 요청은 **Java/Spring·Go·Rust 소스 importer와 여러 HTTP 메서드의 직접 호출 지원**이다. [이번 상세 계획](17-source-importers-plan.ko.md)의 1 → 5 순서와 파일/프레임워크 범위로 구현·검증한다. UPDATE는 PUT/PATCH로 지원한다. 기존의 읽기 전용 제한을 새 직접 호출 경로에서 명시적 effect로 확장하며 회사 API나 기존 관리 Runtime의 쓰기 활성화는 포함하지 않는다.

이후 사용자가 확정한 범위는 **경량 프로토콜 기준 명세 → 설명·탐색 metadata → 공식 시작·모델 연결 예제**의 세 작업이다. [확정 개발 범위](19-protocol-completion-plan.ko.md)의 순서·파일·완료 조건에 따라 모두 구현한다. Python 쓰기나 새 운영 기능을 이 완료 조건에 추가하지 않는다.

### 기존 코드의 처리

- 재사용: OpenAPI 읽기/진단, JSON Schema 처리, HTTP 직렬화·응답 처리, credential provider, context, 기존 호출·오류 인터페이스, MCP SDK 연결.
- 조정: 전체 IR을 반환하는 기본 describe, 모든 capability의 결과를 열거하는 MCP outputSchema, 단순 호출에도 전체 업무 계약을 요구하는 경로.
- 보존: 기존 전체 manifest·composition·review/build·diff·증분·부분 승인. 선택 기능으로 두고 지금 삭제하거나 동작을 뒤집지 않는다.
- 새 경량 실행 경로는 추출 초안의 enabled 플래그를 바꾸는 편법으로 구현하지 않는다. 경량 계약의 schema와 host binding을 검증한다.

### 첫 지원 범위

기존 parser가 처리할 수 있는 OpenAPI 3.0/3.1 중 GET/HEAD·JSON/지원 응답·명시적인 HTTP binding을 첫 사용 대상으로 삼는다. 코드 경로는 등록한 Python 조회 함수부터다. 다른 구현 언어의 API는 HTTP/OpenAPI 경계에서 연결한다.

변경 HTTP 메서드는 기존 adapter의 지원과 활성 runtime의 지원을 구별한다. transport가 POST를 보낼 수 있다는 이유로 업무 쓰기 실행까지 완료했다고 안내하지 않는다. 미지원 항목을 실행 성공으로 표시하지 않는다.

## 3. 검증도 핵심 사용 경로에 맞춘다

### P0-1

주문·배송 OpenAPI에서 선택한 operation을 변환하고 실제 샘플 HTTP를 호출한다. 변환 사실, 직렬화, 원본 응답 검사, 공개 필드, 잘못된 입력/권한/응답의 처리를 확인한다. 라이브러리 예제에서 강제적인 중간 파일이나 review/build 명령이 없어야 한다.

큰 API의 기존 1,254-operation 명세는 파서 범위·진단을 확인하는 고정 자료로 재사용한다. 전체 API를 실행했다거나 업무 관계를 자동 완성했다는 표현은 쓰지 않는다. 네트워크를 추가하지 않고 선택한 route를 fixture로 연결할 수 있다.

### P0-2

같은 기능의 OpenAPI 경로와 Python 등록 경로가 같은 종류의 호출 설명·결과·오류를 제공하는지 확인한다. 입력 schema에 인증 context가 섞이지 않아야 한다. wrapper가 없는 코드의 내부 관계를 추론했다고 주장하지 않는다.

### P0-3

- 실제 MCP client로 변환한 API를 호출한다.
- 같은 설정에서 노출 capability를 1개에서 100개로 늘려도 공통 tools/list에 개별 업무 schema·ID가 누적되지 않아야 한다.
- describe에는 선택한 항목의 입출력과 사용 제약이 남고, 실행 DAG·review 이력·credential은 없어야 한다.
- 원본 API 직접 노출과 a2api의 전체 전달 payload를 비교한다. 도구 정의뿐 아니라 discover/describe/결과까지 포함한다.
- UTF-8 바이트 측정과 실제 모델 tokenizer 측정을 구분한다. LLM을 실행하지 않았다면 모델 성공률을 보고하지 않는다.

기존 관련 테스트도 실행해 재사용 경로가 깨지지 않는지 확인한다. 테스트 개수를 늘리는 것을 별도 목표로 삼지 않는다.

## 4. 지금 추가하지 않을 작업

CI/CD, 변경 호환성/버전 정책 자동화, 자동 재배포, graph/vector DB, 스냅샷 저장 최적화, 다국어 전체 AST 분석기, 범용 FFI, 분산 workflow/승인 플랫폼, 대규모 LLM 평가 서비스는 첫 완료의 필수 작업이 아니다.

기존 구현이 있다는 이유로 이 목록을 먼저 확장하지 않는다. 실제 사용에서 필요한 기능을 확인하거나 사용자가 요청할 때 별도 범위를 잡는다. 지금 그 기능들을 순서대로 수행할 새로운 세부 로드맵도 만들지 않는다.

## 5. 범위가 다시 커지지 않게 하는 규칙

1. 개발 결과는 위 세 사용 결과 중 어디를 완성하는지 설명할 수 있어야 한다.
2. 한 요구를 해결하면서 별도 관리 서비스·승인 파일·사용자 명령을 더 도입해야 한다면, 먼저 기존 모듈 내부 처리로 가능한지 판단한다.
3. 루틴 구현·리팩터링은 범위 안에서 진행한다. 사용자가 지시하지 않은 다음 기능을 임의의 새 목표로 만들지 않는다.
4. 계획을 바꿀 필요가 있으면 막힌 실제 문제, 최소 수정안과 범위 영향을 문서에 남긴다. 선택 기능을 필수 전환 단계로 올리지 않는다.
5. 보고에는 실제로 구현/실행한 것과 예제·계획·추정을 구별한다. 저장 크기, tool 수, 테스트 통과가 토큰 절감·LLM 정확도를 증명하지 않는다.

완료 판단은 “사용자가 이 시작 예제로 자기 API를 전환해 호출할 수 있는가”다. 운영 기능을 많이 갖췄다는 이유로 완료라고 하지 않는다.
