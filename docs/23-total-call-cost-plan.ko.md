# 전체 호출 비용을 줄이는 프로토콜: 확정 개발 계획

작성: 2026-10-30. 이 계획을 먼저 기록한 뒤 1 → 4 순서로 개발한다. 사용자의 최신 목표와 00 문서가 기준이다. 구현 전 API 예시는 계획이며, 실제 사용법은 구현 후 24 문서에 기록한다.

## 목표와 판단 기준

API 수와 무관하게 필요한 기능 탐색과 정확한 인자 호출의 전체 비용을 줄일 수 있는 공통 규칙을 만든다. 같은 실행 계약에서 요청에 필요한 정보만 모델에 제공한다. 소규모에서 항상 우월하거나 대규모·복잡한 모든 업무에서 최적이라고 약속하지 않는다. 이번에는 작동하는 정보 전달 경로와 재현 가능한 비교까지 끝낸다.

정확성은 필수값·타입뿐 아니라 사용자가 지정한 개수·페이지·ID, 누락 정보 질문, 선행 결과 ID 사용, 실패 보고로 평가한다. 자연어 의도 검증기를 새로 만들지 않는다. 이러한 조건을 모델이 놓치면 실패로 기록한다. 입력·원본 응답·공개 응답 검증과 호스트 인증 context는 그대로 유지한다.

전체 비용은 시작 비용, 모델 요청 횟수·실측 usage 토큰·경과 시간, 도구 호출, 탐색/설명 전송, 실제 백엔드 호출, 수정 호출을 구분해 기록한다. schema 예산은 정확히 UTF-8 JSON 바이트로 정의하고 토큰이라고 부르지 않는다. 모델·네트워크 변동을 통제한 보편적 성능 수치는 주장하지 않는다.

## 1. 공통 계약과 정보 전달 규칙 확정

- `a2api-call/0.1` descriptor와 discover/describe/invoke wire를 유지한다.
- 새 호스트 바인딩 규칙 `a2api-tools/0.1`을 24 문서에 정의한다. 이는 모델에게 전달할 function tools 표현이며 새로운 서버·관리 단계가 아니다.
- 호스트가 알고 있는 기능은 처음부터 정확한 입력 schema로 제공한다. 모르는 기능에는 검색 도구만 제공하고, 한 번의 모델 검색 후 호스트가 discover/describe를 처리한다. 다음 모델 요청의 tools에 호출 가능한 schema가 들어간다.
- 선택한 도구의 인자는 원래 inputSchema 그대로다. id/version/catalogVersion은 호스트가 보관하고 invoke에 넣는다. 결과 envelope와 오류는 유지한다.
- 출력 schema는 모델 function parameters에 중복 전송하지 않고 서버/호스트에서 검증한다. 필수값·enum·$defs 등 입력 제약은 자르거나 완화하지 않는다.
- 같은 호스트 세션은 선택한 정의를 재사용한다. 활성 도구 집합은 전체 JSON 바이트 예산 안에서 유지한다. 예산 초과 시 도구 전체 단위로 교체하거나 명시적 거부한다. 대형 schema를 조용히 축약하지 않는다.
- catalog가 바뀌면 이전 바인딩을 폐기한다. context와 서버가 바뀌면 새 세션을 만든다. 쓰기를 자동 재시도하지 않는다. MCP tools/list는 검색 전후 동일한 3도구다.

산출물: 00/03 갱신, 이 계획, 24 명세·사용법. 완료 조건: 준비된 기능/미지 기능/후속 호출/계약 변경의 규칙과 한계를 문서로 구분한다.

## 2. 경량 호스트 바인딩 구현

예정 파일: `src/a2api/tool_session.py`, 공개 export, `tests/test_tool_session.py`.

- `ToolSession`은 기존 Application/ConvertedAPI 또는 연결된 MCP client를 받는다. 외부 모델 SDK나 DB 의존성을 추가하지 않는다. 기존 3도구 client도 보존한다.
- 호스트의 명시적 초기 기능 선택, task query 검색, 정확한 function 정의 생성, 불투명한 충돌 방지 이름과 서버 binding 매핑, 호출 전달을 제공한다.
- schema 예산과 최근 사용 기준의 도구 집합을 유지한다. 검색 결과에는 선택한 이름/짧은 설명과 미수록 이유를 반환하고 큰 schema를 결과와 tools에 두 번 싣지 않는다. 검색 limit과 예산은 호스트가 정한다.
- 호출 직전 선택한 입력 schema를 검사하고 원래 invoke 검증을 유지한다. 성공 출력도 보관한 outputSchema로 검사한다. 잘못된 이름·입력·변경된 계약은 백엔드 실행 없이 구조화된 오류로 반환한다.
- 세션은 한 서버/한 trusted context에 귀속된다. 공유 인증 캐시, 자동 권한 추론, 벡터 검색, 업무 관계 추론은 추가하지 않는다.

완료 조건: 로컬 함수와 실제 HTTP 전환 객체에서 호출, 검색 한 모델 단계 후 실행 가능한 도구 생성, 후속 호출 재사용, 작은 예산/큰 schema/잘못된 인자/계약 변경/권한 보존, 1,000개 카탈로그의 선택 노출을 테스트한다.

## 3. 실행 예제와 모델 호스트 연결

예정 파일: 기존 `examples/model-client/client.py`의 선택적 `--binding selected` 경로, `examples/tool-session/` 실행·평가 예제, 관련 테스트와 사용 문서.

- 기존 기본 3도구 경로는 유지한다. 선택 도구 경로에서 모델은 검색 또는 정확한 업무 인자만 작성한다. 호스트가 tools를 매 모델 요청에 다시 구성한다.
- `--known`으로 호스트가 아는 API를 바로 제공할 수 있다. API 개수 기준으로 강제 전환하지 않는다. 사용자가 선택한 모드는 명시적으로 기록한다.
- 주문→반환된 배송 ID→배송 조회, 같은 대화의 후속 요청, 저장소→이슈 페이지 조회를 실행한다. 데이터 관계는 기존 응답·명시적 wrapper를 사용하며 새 DAG/그래프 엔진은 만들지 않는다.
- 모델 입력·도구 결과의 원문 reasoning과 credential은 저장하지 않는다. 모델 usage, 실제 인자, 실행 결과, 시간은 선택적 로컬 기록으로 남긴다.

완료 조건: 실제 stdio에서 원래 tools/list는 그대로이며 선택한 업무 도구로 호출된다. 기존 quickstart와 새 선택 경로의 실행 명령이 각각 동작한다.

## 4. 규모·요청 유형별 평가와 보고

- 결정적 검증: 2개와 1,000개 등록 카탈로그, 알고 있는 기능/검색 필요 기능, 단순/후속/선행 결과 의존 호출, 잘못된 입력·미확정 입력·실패를 확인한다. 1,000개 fixture가 실제 대규모 업무 성공률을 증명한다고 표현하지 않는다.
- 실제 Muse Glimmer: 같은 업무·입출력·반환 필드·검색 방식을 유지하고 기존 공통 3도구와 새 선택 도구 경로를 비교한다. 알려진 소규모 기능에는 보통의 직접 function tool 기준도 포함한다. 큰 카탈로그는 동일 검색기를 쓰는 일반 검색+function 도구를 기준으로 하며 전체 schema 덤프를 유일한 비교군으로 삼지 않는다.
- 주문·배송 로컬 HTTP와 기존 GitHub 공개 조회로 검증한다. 큰 카탈로그에는 구별 가능한 합성 방해 기능을 추가하고 그 한계를 기록한다. 실제 GitHub는 저장소/이슈 두 기능만 호출하며 API quota를 먼저 확인한다.
- 같은 대화의 후속 요청을 포함하고 startup을 따로 기록한다. 모델 실패/초과 호출/동률/개선 없음도 보존한다. 반복 수·각 시나리오·순서와 한계를 보고한다. 비용 우월성은 완료 조건이 아니다.
- 관련 회귀 테스트 후 전체 테스트를 한 번 실행한다. 결과·재현 명령을 문서와 작은 evidence JSON에 정리하고 사용자 작성자로 커밋·GitHub push한다. 로컬 대화 원문·대형 artifacts는 커밋하지 않는다.

## 범위 고정

새 CI/CD, 자동 재배포, API 변경 관리, 임베딩/검색 서비스, 자동 의도 파서, 자동 업무 그래프, 병렬 실행 스케줄러, 전체 언어/프레임워크 지원은 이번에 추가하지 않는다. 모델이 잘못 준 숫자를 임의로 보정하거나 실패한 실행을 재측정으로 대체하지 않는다. 작은 구현 변경은 이 네 결과 안에서 처리하고, 불가피한 계획 조정은 실제 원인·최소 영향만 이 문서에 기록한다.
