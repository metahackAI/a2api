# 실제 카탈로그 결과에 따른 전체 비용 개선 계획

2026-10-30 · 상태: **1번 구현·재검증 완료, 2·3번 미착수**. 이 계획은 [최초 결과](27-real-github-evaluation-results.ko.md), [원 평가 범위](26-real-github-evaluation-plan.ko.md)를 근거로 작성했다. 이후 사용자가 1번만 요청해 [범위 기록](29-search-improvement.ko.md) 후 구현하고 [같은 Muse 요청으로 재검증](30-search-improvement-results.ko.md)했다. 아래 최초 관찰과 남은 계획은 보존하며, 2·3번은 다음 지시 전까지 진행하지 않는다.

## 목표와 우선순위

먼저 대규모에서 필요한 API를 실제로 찾고 사용자 조건을 만족하게 만든다. 성공한 소규모의 정확성을 유지하면서 검색·계약 설명·반복 전송·실행을 합친 비용을 줄인다. 실패를 빨리 끝낸 것만으로 정확한 호출이 더 효율적이 됐다고 주장하지 않는다.

계획을 작성할 때 최초 실행에서 관찰한 근거는 다음과 같다.

- 633개에서 두 모드 모두 필수 계약 조합을 찾지 못해 12회 모델 단계 제한에 도달했다. 저장소 질문의 `repos/get` 순위는 실제 질의에서 38~241위, 브랜치 목록은 9~259위였다. 본문 substring 일치 개수와 ID 사전순이 기능 적합성을 제대로 반영하지 못했다.
- 연쇄 질문에서 `repos/get`을 도구로 제공한 경우도 있었지만 `repos/get-commit`은 제공되지 않았다. 먼저 가능한 조회를 실행하지 않고 검색을 계속한 모델 행동도 관찰했다. 검색 품질과 전달 정보가 함께 필요하다.
- 검색 결과에는 moreAvailable이 있지만 현재 호스트 도구에 다음 페이지를 요청할 인자가 없다. 비슷한 질의로 같은 후보를 다시 받아 비용이 누적됐다.
- 정확한 `github.repos.get`의 prime도 유사 접두어 항목이 많으면 AMBIGUOUS_SELECTION으로 거부된다. 알려진 기능의 준비 경로도 실제 카탈로그에서 보완해야 한다.
- 원본 전체 응답을 전송했고, 소규모에서도 평균 여러 검색이 필요했다. 도구 정의와 대화가 반복 전달됐다. 원래 계획한 select는 GitHub의 `x-github-breaking-changes` annotation 때문에 거부됐다.
- 주 비교의 모델 외 시간은 ordinary 약 5.1초, a2api 약 7.4초인 반면 모델 시간은 각각 약 559초, 576초였다. HTTP/검증 미세 최적화보다 탐색 수렴과 모델에 주는 정보량을 먼저 다룬다.

## 1. 필요한 기능을 찾고 검색을 수렴시키기

**완료.** 정확 ID·필드별 검색 index·조건부 3페이지를 구현했다. 전체 회귀 290개와 실제 MCP stdio 페이지 전환이 통과했고, 같은 Muse 평가에서 8개/633개 모두 두 방식이 각 6/6을 완료했다. 상세 규칙·한계·비용은 [30 문서](30-search-improvement-results.ko.md)에 기록했다. 모델의 more 사용은 0회였으므로 성공 회복을 pagination 효과로 해석하지 않는다.

변경 범위: `src/a2api/mcp_application.py`, `discovery_metadata.py`, `conversion.py`, `native.py`, `tool_session.py`, 관련 테스트와 24 문서. 기존 관리 Runtime의 정책 엔진·사용자 권한 시스템을 새로 만들지 않는다.

### 1.1 원본에 근거한 검색 index

- ID, 원본 operationId, 짧은 summary, 입력/공개 출력의 주요 field 이름, 보조 설명을 구분한다. 긴 Markdown 본문에 흔한 단어가 많이 나온다는 이유만으로 상위가 되지 않게 한다.
- `/`, `.`, `_`, `-`, camelCase 경계를 동일한 규칙으로 token화한다. `default_branch`와 `default branch`처럼 원본 표기의 차이를 처리한다. 자주 등장하는 get/GitHub 같은 단어와 드문 업무 단어의 기여를 구분한다.
- 기존의 명시적 keywords와 한글 검색이 퇴행하지 않는지도 검사한다. GitHub 전용 정답 사전이나 새로운 다국어 NLP 서비스를 만들지 않는다.
- 완전한 capability ID는 정확 일치로 처리한다. 유일한 ID가 prefix 이웃 때문에 거부되지 않아야 한다. 버전이 실제로 여러 개인 경우는 임의로 고르지 않는다.
- summary의 동작(list/get)·resource 일치와 공개 output field를 높은 근거로 사용한다. 중첩 응답에 우연히 들어 있는 repository 객체가 top-level repository 조회와 같은 점수를 받지 않게 한다. 필요한 root/$defs 해석만 제한적으로 수행하고 순환·복합 schema는 진단 가능한 범위로 처리한다.
- field/metadata는 서버 index에 보관한다. 전체 출력 schema나 실행 IR을 모델 검색 결과에 싣지 않는다. 특정 평가 질문에만 맞춘 keywords·정답 operation 우대는 넣지 않는다.

### 1.2 기존 검색 도구의 조건부 다음 페이지

- 공통 MCP 도구 세 개는 유지한다. 기존 wire discover의 cursor를 호스트가 관리한다. 호스트 검색에 선택적 `more` 인자를 두어 같은 질의의 다음 후보를 요청할 수 있게 한다. query만 보내는 기존 사용법은 유지한다.
- 새 필수 resolve/승인/build 단계는 만들지 않는다. 검색 한 번 뒤 실행 가능한 정확한 입력 schema를 제공하는 경로를 유지한다. 추가 페이지는 필요한 경우에만 요청한다.
- 같은 질의·후보가 반복되는 경우 새 정보가 없음을 명시한다. 초기 기본값은 질의당 최대 3페이지(후보 9개), 모델 12단계 예산으로 고정하고 전체 카탈로그를 자동 순회하지 않는다. cursor는 현재 catalog/query/caller/limit에 묶고 변경되면 폐기한다. 검색 순서가 바뀌면 기존 cursor를 새 순서에 적용하지 않는다.
- 단순히 limit를 크게 늘리거나 첫 후보만 강제 선택하지 않는다. 우선 후보 수 3과 16KB 예산을 유지해 검색 개선 효과를 분리한다.

완료 조건: 관찰한 질의의 실패를 오프라인 rank 재현으로 검증하고, 평가에 사용하지 않은 질의에서도 정답이 후보에 포함되는지 검사한다. 정확 ID/유사 접두어/복수 버전/다음 페이지/계약 변경/예산/권한 context 검사를 통과해야 한다. 이후 실제 Muse에서 8개와 633개 모두 단순·연쇄 요청을 완료해야 한다. 값/인자를 임의로 보정해 통과시키지 않는다.

## 2. 호출에 필요한 결과 의미와 데이터만 전달하기

예정 변경: `src/a2api/conversion.py`의 기존 select 처리, `tool_session.py`의 function 설명 생성, 같은 설명·projection을 쓰는 평가 대조군, 관련 테스트·사용 문서.

- 먼저 원본 JSON Schema 제약과 무해한 annotation을 구별해 `repos/get`의 기존 top-level select가 동작하게 한다. schema 조합/조건 같은 제약은 plain object처럼 취급하지 않는다. 입력·원본 HTTP 응답 검증을 그대로 실행한 뒤 공개 필드를 선택한다.
- 평가 앱에서 저장소의 full_name/default_branch/stargazers_count/archived, 커밋의 sha/stats/html_url을 선택한다. 양쪽 비교군에 같은 설정을 적용한다. 서버가 전체 JSON을 계속 반환하므로 원 API 네트워크 바이트가 줄었다고 주장하지 않는다.
- 공개 output schema에서 실제 반환 필드·출처/nullable 등 필요한 의미만 짧게 function 설명에 보탠다. 모델이 “Get a repository”가 요청한 default_branch를 제공하는지 알 수 있게 한다. 전체 output schema를 모델 도구에 다시 넣지 않는다. schema에 없는 의미·원인·업무 관계를 추측해 작성하지 않는다.
- 입력 schema의 필수값·enum·범위·$defs와 인증 context는 변경하지 않는다. 원본에 없는 값을 default/null로 채우지 않는다. 입력 오류·원본 응답 오류·공개 응답 오류·실행 여부 불명확의 구분을 유지한다.
- 현재 top-level select를 다루며 범용 JSONPath, 자동 자연어 의도 파서, 새 graph/workflow/배포 기능은 추가하지 않는다. 브랜치 배열은 그대로 사용한다.

완료 조건: 원 응답의 잘못된 필드/타입은 projection 뒤에도 차단되고, 필수/선택/null/참조 의미가 보존돼야 한다. 같은 공개 결과와 설명을 사용하는 일반 호스트와 비교한다. 한 번의 개선으로 항상 토큰이 감소한다고 가정하지 않고 실제 usage로 판정한다.

## 3. 같은 요청과 보류한 요청으로 정확성·전체 비용 재검증

예정 변경: 기존 `examples/real-github-evaluation`과 관련 테스트·evidence·결과 문서만 갱신한다. 평가 서비스나 CI를 추가하지 않는다.

1. 이번 24질문·같은 모델 설정·동일한 순서 교대 규칙을 재사용한다. small의 현재 6/6(각 모드)을 유지하고 large도 각 모드 6/6을 완료 목표로 한다. 이것이 전 세계 API의 성공률 100%라는 뜻은 아니다.
2. 1번 작업 뒤 같은 평가로 성공 회복과 검색 비용을 확인한다. 그 실행을 보존한 뒤 2번 작업의 전달량·전체 비용 효과를 확인한다. 같은 실패를 지우기 위한 임의 재실행은 하지 않는다.
3. 검색을 조정할 때 보지 않은 질의/기능을 별도 holdout으로 둔다. 공개 repo의 languages, license, tags, contributors 등 현재 source와 실제 응답이 검증되는 조회에서 6요청×두 모드=12질문으로 한정한다. 질문과 채점 조건은 모델 실행 전에 고정하고 성공/실패에 따라 교체하지 않는다. source/권한/응답 drift 문제는 모델 오류와 구별한다. 실패도 보고한다.
4. ordinary와 a2api 모두 같은 개선 검색·설명·입출력·예산을 적용한다. 대조군을 약하게 만들어 우위를 만들지 않는다. 성공 여부가 다른 실행의 토큰만 비교해 우월하다고 하지 않는다.
5. 전체 usage·시간(공통 카탈로그 준비/세션 준비 포함)·모델 왕복·내부 탐색/설명·실제 GitHub 호출과 추가 조회를 모두 기록한다. 실패 비용을 포함한 성공당 비용도 본다. 성공이 0이면 해당 비용은 정의하지 않는다. 바이트 감소는 실제 토큰 감소와 구별한다.

완료 조건: 입력·결과·value-flow·사용자 개수/페이지 조건의 회귀가 없어야 한다. 같은 정확도를 만족한 실행 사이에서 비용 감소가 관찰된 범위만 보고한다. 지연 차이가 작거나 일관되지 않으면 개선으로 단정하지 않는다. 조건을 못 만족하면 미완료·실패 원인을 기록하며 검증을 약화하지 않는다.

## 이번 계획의 경계

위 1 → 2 → 3만 후속 개발 범위다. embedding/vector DB, 별도 LLM router, 새 agent SDK, 자동 API 조립 엔진, 다단계 승인/관리, CI/CD는 포함하지 않는다. 실행 검증이나 인증을 제거하는 최적화도 하지 않는다. 일반적으로 잘 만든 검색+function 호스트보다 프로토콜이 항상 적은 추론 비용을 갖는다는 주장을 목표로 삼지 않는다. 같은 규약에서 필요한 정보를 생성·찾기·검증·재사용하는 실제 비용을 낮추는 것이 목표다.
