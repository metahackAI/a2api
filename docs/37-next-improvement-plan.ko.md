# a2api 다음 개선 계획(1.1 이후)

작성일: 2026-10-31 · 상태: **계획(사용자 확정 전, 구현하지 않음)** · 근거: [34 문서](34-completion-results.ko.md)의 holdout 판정·사후 분석

## 0. 현재 위치

| 축 | 1.0에서 확인한 것 | 남은 문제 |
|---|---|---|
| 컨텍스트 | 작업당 약 4.5–7k 토큰으로 API 규모와 거의 무관(명세 방식 대비 −16%~−95%) | 다단계 작업은 결과가 대화에 누적돼 7k를 넘는다 |
| 속도 | 235개 API에서 −27%~−43% | 19·55개 API에서 명세 function 방식보다 10–18% 느림(holdout). 원인은 첫 단계 추론 출력이 약 10–20% 길고, 기준선의 큰 정적 prompt가 서버 prefix cache로 싸지는 것 |
| 정확도 | 세 방식 모두 98.8–100% | 이번 모델·작업에서는 a2api의 정확도 이점을 보여 주지 못함(상한) |
| 사전 선택 | 단일 의도 질문은 거의 항상 필요한 기능을 포함 | 값만 있는 질문(이메일 등)·여러 리소스를 잇는 질문에서 놓침 → 검색 왕복 |
| 변환 범위 | Spring MVC·Go net/http·Rust Axum·Python 함수·OpenAPI JSON 본문 | Gin/Echo/Chi, Actix, NestJS/Express, FastAPI 소스, multipart·비JSON |
| 평가 | 합성 API 1종, 모델 1종(30B, 64k, prefix cache 있음) | 다른 모델·provider·실제 API·더 큰 API에서의 효과 미측정 |

## 1. 개선 항목(우선순위 순)

### P1. 효과가 나타나는 조건을 넓게 측정한다(주장 근거 먼저)

1.0의 결론은 "이 모델·이 작업"에 한정된다. 개발보다 측정을 먼저 넓혀, 어느 조건에서 a2api가 이기고 지는지 확정한다.

| 항목 | 가설 | 측정 | 완료 조건 |
|---|---|---|---|
| 1-1 모델·provider 확장 | prefix cache가 없거나 토큰 과금이 큰 provider에서는 a2api의 속도·비용 이점이 커진다 | 같은 하네스에 Anthropic/OpenAI 계열 1종 이상 + 작은 문맥(8–32k) 로컬 모델 1종. provider usage로 **금액**도 계산 | 모델 3종 이상의 holdout 표, 조건별 승패 정리 |
| 1-2 문맥을 넘는 API | 1,000개 이상 operation에서는 명세 전달이 문맥 초과·선택 오류로 실패하고 a2api는 유지된다 | 생성기로 1,000/2,000 operation 규모 추가, 실제 GitHub REST 전체 GET 633개 재평가 | 규모별 정확도 곡선, 문맥 초과 비율 |
| 1-3 더 어려운 작업 | 이름·의미가 비슷한 기능 구분, 잘못된 입력 교정, 권한 거부, 페이지 수집에서 정확도 차이가 난다 | holdout 2세트 추가(작업 내용을 실행 전에 고정) | 정확도 차이가 통계적으로 구분되는지(반복 3회) |

### P2. 소·중규모 지연을 줄인다

| 항목 | 가설 | 실험 | 채택 기준 |
|---|---|---|---|
| 2-1 cache 친화적 도구 배치 | 사전 선택 결과가 질문마다 달라 서버 prefix cache를 못 쓴다. 자주 쓰는 핵심 함수를 고정 순서로 앞에 두고 나머지만 바꾸면 첫 요청 지연이 준다 | 고정 core + 가변 tail, 카탈로그 순서 정렬, 전체 제공 경계(10KB) 재조정 | dev 4언어에서 중앙값·평균 지연이 spec-tools 이하, 토큰 증가 ≤ 20% |
| 2-2 함수 이름·설명 표현 | `shop_ticketcontroller_list` 같은 이름은 모델이 해석에 더 많이 추론한다. operationId·HTTP 경로 기반 별칭(`listTickets`, `list_tickets`)이 추론을 줄인다 | `naming="operation"` 옵션, 호스트 별칭 표 | 첫 단계 출력 토큰·지연 감소, 정확도 동일 |
| 2-3 결과 표현 최소화 | 성공 결과의 envelope(`status`)를 줄이면 토큰·추론이 준다 | `render(..., style="data")` 실험 | 토큰 감소, 실패 구분 정확도 유지 |
| 2-4 다단계 왕복 감소 | 복잡 작업은 3–5회 왕복이 지연의 대부분이다. 개발자가 관계를 명시한 조합 기능(주문→배송)이나 독립 조회 일괄 호출이 왕복을 줄인다 | 기존 composition DAG를 직접 호출 경로에서 쓰는 방법 검토, `invoke` 일괄 요청은 프로토콜 확장 후보로만 설계 | 복잡 작업 평균 왕복 ≥ 1회 감소, wire 호환 유지 |

### P3. 사전 선택 재현율을 높인다

| 항목 | 내용 | 평가 |
|---|---|---|
| 3-1 값 유형 신호 | 질문 속 이메일·URL·전화번호·ID 접두어(`ORD-`, `T-`)를 필드 이름·리소스와 연결하는 일반 규칙 | dev로 설계, **새 holdout**으로 판정(기존 holdout 재사용 금지) |
| 3-2 다중 의도 분할 | 쉼표·연결어 기준으로 질문을 나눠 각각 검색한 결과를 섞는다 | 다단계 질문 재현율, 검색 왕복 수 |
| 3-3 호스트 사용 기록(선택) | 같은 호스트에서 성공한 질의-기능 쌍을 사전 선택에 반영 | 개인정보·권한 경계 검토 후 결정 |

### P4. 변환 범위를 넓힌다

| 항목 | 내용 |
|---|---|
| 4-1 OpenAPI | multipart/form 본문, 비JSON 응답(텍스트·파일 메타), nullable query 직렬화, 2xx schema 없는 operation의 명시 설정(GitHub 미지원 26개 기준) |
| 4-2 소스 importer | Go Gin/Echo/Chi, Go query 정수 추론(`strconv.Atoi` 사용 시 integer), Rust Actix·nest/merge router, Serde enum, Spring WebFlux, TypeScript NestJS/Express, Python FastAPI/Flask(소스 기반) — 실제 요청이 있는 언어부터 |
| 4-3 언어별 의미 보완 | Go처럼 required·enum이 코드에 없을 때 import 보고서에 "summary에 필수 입력·허용 값을 적으라"는 경고, 빈 query 값 처리 차이 진단 |

### P5. 안정성·운영

| 항목 | 내용 | 비고 |
|---|---|---|
| 5-1 쓰기 멱등성 | `requestId`를 backend `Idempotency-Key` 헤더로 전달하는 선택 옵션, `OUTCOME_UNKNOWN` 뒤 확인 조회 패턴 문서화 | 자동 재시도는 계속 하지 않음 |
| 5-2 CI·배포 자동화 | GitHub Actions(테스트·wheel 빌드), PyPI trusted publishing | **사용자 승인 후**에만 착수(AGENTS 규칙) |
| 5-3 영어 문서 | 전환 가이드(36)·호출 명세(20)·도구 표현(24)의 영어판 | PyPI 사용자 대상 |

## 2. 진행 순서와 규칙

1. **P1 → P2 → P3 → P4 → P5** 순서. P1 결과로 P2·P3의 우선순위를 다시 정한다(예: 문맥 작은 모델에서 이미 크게 이기면 P2보다 P3·P4).
2. 개선은 dev 작업으로만 조정하고, 판정은 실행 전에 해시를 기록한 새 holdout으로 한다. 이미 본 holdout으로 다시 판정하지 않는다.
3. 실패·provider 오류를 지우지 않고, 바이트와 토큰, 합성 API와 실제 API 결과를 구분해 보고한다.
4. wire(`a2api-call/1.0`)와 MCP 세 도구는 호환을 유지한다. 바뀌는 것은 호스트 표현(`a2api-tools`)과 importer다. 프로토콜 확장(일괄 호출 등)은 설계·측정 후 별도 버전으로 제안한다.
5. 각 항목은 이 문서에 "실험 → 결과 → 채택/기각"을 기록하고, 채택한 것만 기본값을 바꾼다.

## 3. 지금 하지 않는 것

자동 API 관계 추론 그래프, vector DB/embedding 검색 서버, LLM router, 승인·관리 플랫폼, 사용자 요청 없는 운영 기능. 필요성이 측정으로 확인될 때 별도로 제안한다.
